# axe

BYOK CLI coding agent. Design constraints for anyone working on it — see [README.md](README.md) for usage and [CONTRIBUTING.md](CONTRIBUTING.md) for the checks.

## Rules for anyone (human or agent) editing this repo

- The core is the loop, the tool set, the context manager, and the thread store. Nothing else goes in `src/core`.
- No provider SDK types leak past `src/providers`. Everything else speaks `Message` and `Block`.
- Seven tools, plus `task`. Adding a ninth needs a written reason. New capability goes in a plugin or a skill.
- `task` is the standing example of what a written reason looks like: it is the only tool whose product is not information but a second context window. A search that would cost the main thread twenty file reads costs it one paragraph. No arrangement of the other tools buys that.
- `web_fetch` is the second written reason: it is the only tool whose subject is not this machine. `curl` through `bash` reaches the same bytes, but what comes back is markup: 30KB of a modern page is tags and script, not prose, so the model reads noise or nothing. `web_fetch`'s product is the page's text at a bounded size, with search-engine redirect links unwrapped so a results page becomes followable. No arrangement of the other tools buys that either.
- There are exactly two extension points and they are different in kind. **A skill is a document**: markdown, no runtime, discovered by description, read with `read_file` when it becomes relevant. **A plugin is a program**: a module that exports tools. If a proposed feature is neither a document nor a tool, it does not belong in either, and probably does not belong in axe.
- A skill costs one line of system prompt until it is used. Keep it that way: never inline a skill body into the prompt, and never add a tool whose only job is to read a skill.
- Plugins run with the user's full privileges and always will. Do not build a fake sandbox; document the trust instead.
- A broken plugin degrades to a notice. Nothing a plugin does may prevent axe from starting.
- An MCP server is a plugin that speaks a protocol instead of exporting functions, so it lives behind the same `plugins` switch, obeys the same shadowing and startup rules, and its tools are never read-only: an unknown side effect scheduled in parallel is a race the model cannot see.
- The edit check (`checkCmd`) is the feedback loop that replaces a language server: the project's own typecheck runs after every successful `edit_file` and its failures ride back inside the same tool_result. It is project-scoped config because it only ever runs after the model has already edited that repo, at which point the model runs project commands through bash anyway; it is still printed at startup so nothing runs unseen. A failing check is appended to a successful result, never turned into a tool error: the edit happened and the model needs to see both.
- A turn is a tree of concurrent work, and one status row cannot say so. The activity panel is the answer: one row per running tool or subagent, children indented under the agent that spawned them, released back to the transcript when the turn ends. It reuses the scroll-region machinery the palette and the `@` picker already use, and yields to both — a list the user just opened outranks something the agent is doing in the background. Everything that can be computed without a terminal lives in `src/ui/activity.ts` as pure functions, because escape codes can only be verified by looking at them.
- Progress bars are indeterminate and stay that way. No tool reports how far along it is, and a bar that invents a percentage is a bar that lies. The honest signals are the spinner, the elapsed clock, and the row count.
- A subagent's visibility is a setting (`agentTrace`), not a default, because the two failure modes point opposite ways: silence makes a forty-second search indistinguishable from a hang, and full streaming makes four parallel subagents into four interleaved monologues. `compact` is the default because the panel can show concurrency that a transcript cannot. What never changes is that a subagent's tool calls stay out of the transcript in every mode — keeping its file reads out of the caller's context is the entire reason it exists.
- An image enters a prompt as a typed path, because a terminal cannot paste pixels. Any typed path to an image file is attached; `@` still only ever inserts the path, so it remains a typing aid. Only the user's message is expanded, never text a model wrote.
- A review check is a document, like a skill: markdown in `.axe/checks/`, one read-only subagent per check, and a subagent reviewing one check reports on that check only.
- A custom subagent role is a document too: markdown in `.axe/agents/` or `~/.axe/agents/`, where the body is the brief and the frontmatter carries a description and, at most, which internal route it runs on. It may not name a model, and it may not shadow `search` or `oracle`. It costs one line of the `task` tool's description, the way a skill costs one line of the prompt. This is the extension point for "a different kind of subagent"; a plugin is still the extension point for "a different tool".
- The cost hard stop is opt-in (`cost.hardStopUsd = 0` by default) and the warning is not. A run killed at a round number in the middle of a task costs more than it saves, because the work is repeated from the top. A user who wants a ceiling for an unattended run sets one on purpose.
- `bash` runs in the foreground by default and in the background on request, and background mode is a field on the same tool rather than an eighth tool: it is the same command, and what changes is only whether axe waits. A backgrounded command returns a log path immediately, keeps running past the turn, and is read back with `read_file` or `grep`. That is what closes the feedback loop for a dev server or a watcher, which has no exit code to wait for. The credential scrub applies identically in both modes.
- A plugin tool may not shadow a core tool name. Shadowing `read_file` or `bash` would be a quiet way to hijack the agent.
- Subagents get read-only core tools, built from a fresh `coreTools()`, never from the parent registry, and never plugin tools. A subagent therefore cannot edit, cannot run bash, cannot run third-party code, and cannot spawn another subagent.
- Subagent usage must be added to the parent session's usage. An unrolled subagent makes the cost limit a lie.
- Subagents are spawned by a model, not a person, so their concurrency is capped by config (`maxParallelSubagents`), not by judgement.
- No slash commands, ever. They are a second language the user cannot see, and they make every message beginning with `/` ambiguous. The palette is the answer to "how do I discover what this can do".
- The palette is a UI affordance, not an API. Nothing in it is visible to the model, and no entry may do something the user could not do by typing or by pressing a key. An entry that needs a new capability is a feature request, not a palette entry.
- `@` is a typing aid and must stay one. It may only leave behind a path the user could have typed. It may not attach file contents, annotate the prompt, add a tool, or become visible to the model in any other way. The moment it does, it is a slash command with a different character.
- An error is classified where it is printed, never where it is thrown. `src/errors.ts` reads the errors the layers already produce — a status on `HttpError`, a `kind` on `KeyError`, the `mcp <name>:` prefix the client writes — and returns a surface, a stable code, a one-clause message and a next step. The alternative was an `AxeError` base class, which is forty edited throw sites across five adapters for no change in behaviour and a type every recorded adapter test would have to learn. The rule that keeps it honest: an error nothing recognises keeps its message verbatim and gets **no** next step, because a wrong suggestion is followed. Tool errors are the deliberate exception and stay prose — the reader of a `tool_result` is the model.
- The debug log is the one piece of state that does not travel explicitly, and only because both explicit routes are worse: a field on `ToolCtx` changes a type every tool and every test constructs, and a field on `StreamOptions` widens the `Provider` contract for a diagnostic. So `src/debuglog.ts` is a module singleton, initialised from `src/cli.ts` and nowhere else, off unless `--debug`/`AXE_DEBUG`/a trusted `debug = true` asks for it, and announced at startup so nothing is written unseen. It holds the current turn id, which is how a retry logged from inside a provider adapter is correlated without the adapter learning that turns exist. It writes names, ids, counts, durations and status codes — never prompt text, never tool arguments, never a key, because a tool argument can hold a password and a debug file is what people paste into an issue.
- `debug` is trusted-scope config like `plugins` and `keySource`. A cloned repo that could turn it on would be writing files under someone's home directory on the next run.
- `axe doctor` is a command, not a tool: the agent has `bash`, and this exists for the human trying to work out why nothing runs. It reaches no provider and spends nothing, so it sits with the commands that return before a session exists — the setup that is broken must still be able to run the thing that explains why. `axe mcp doctor` stays as the narrow form and shares `probeServer`, so the two cannot disagree. Only `fail` sets the exit code: a CI job that goes red over an unapproved optional server teaches people to stop running the check. Every check is a function returning a row in `src/doctor.ts`, and the formatting and exit code belong to `cli.ts`, because a row is asserted by calling it while a printed line costs a fork per case.
- Do not add a feature that only exists to work around a weak model. Those become dead weight in eight weeks.
- Zero runtime dependencies in the core. Node/Bun standard library only. That includes the terminal UI: no Ink, no blessed, no chalk.
- Tabs for indentation, no semicolons, double quotes.
- No TypeScript parameter properties. Node's strip-only type stripping rejects them.
- A new provider is a new file in `src/providers` implementing `Provider`. Do not branch on provider name anywhere else.
- Anything a provider cannot answer honestly, such as token counts and prices, must be documented as an estimate at the call site.
- A new provider ships with recorded SSE frames in `scripts/adapter-test.ts`. An adapter with no replay test does not count as written.
- Tests fake the boundary, never the code under test. Replace `globalThis.fetch`, do not add a seam to the adapter just to make it testable.
- Output formatting lives in `src/ui`. The loop speaks to a `UI`, never to stdout, so that a new surface (JSON, TUI) is a new file rather than a branch in the loop. That includes the line-based surface: `src/ui/plain.ts` is what `-x`, `--plain`, and a pipe get, and it is a peer of `tui.ts` and `json.ts` rather than something the entry point keeps to itself.
- `src/cli.ts` wires things together and owns the commands. It does not decode argv and it does not format output: `parseArgs` is a pure function in `src/args.ts` and the surfaces are in `src/ui`. Both moved out for the same reason — a pure function is checked by calling it, while anything left in the entry point can only be checked by spawning a process, which costs a fork per case and so only ever covers the cases someone bothered to spawn.
- The help page is hand-written and therefore drifts. `cli-test` reads the flags back out of it and runs each one through the parser, so a flag `--help` lists is a flag that exists. Adding a flag means adding it to `HELP` too, or the check fails.
- A command that takes no arguments rejects them. `axe threads --json` doing the bare thing and exiting 0 is the same failure as a mistyped flag reaching the model: the user asked for something and quietly got something else. `ARGLESS` in `src/args.ts` is the list.
- `axe update` writes an executable file, so it fails closed. It installs nothing that is not listed in the release's `SHA256SUMS`, and it replaces nothing whose basename is not `axe`. A checksum mismatch is an error, never a warning.
- The version lives in `src/version.ts`, not in package.json, because a compiled binary cannot read package.json. `release-test` fails when the two drift.
- A release asset is produced by `npm run release` or it does not exist. Hand-uploading a binary with no checksum line makes it uninstallable, which is the intended failure.
- Anything in the TUI that can be a pure function or a plain class must be one. Escape codes are untestable; key decoding, line editing, history, fuzzy matching, and palette selection are not, and they are where the bugs live. The two biggest now have files of their own — `src/ui/keys.ts` decodes stdin and `src/ui/editor.ts` is the buffer and its bindings — and neither may acquire a terminal write. `tui.ts` re-exports both so an importer does not have to know where they moved.

## Invariants the loop must preserve

1. `tool_result` blocks appear in the same order as their `tool_use` blocks.
2. Every `tool_use` gets a `tool_result`, including cancelled and failed calls.
3. The `signature` on an Anthropic `thinking` block survives the round trip.
4. Messages are persisted to the thread file as they are produced, not at end of turn.
5. Compaction never cuts between a `tool_use` and its `tool_result`. The split point is always a plain user turn.
6. A failed token count or a failed summary degrades to "no compaction". It never aborts the turn.
7. A compaction writes a snapshot to the thread, so `--continue` resumes the compacted context.
8. Queued input is injected only at a step boundary, and only after the `tool_result` blocks in that message. It never starts a second concurrent turn.
9. `--stream-json` writes exactly one JSON object per line, each with a `type`. Adding an event type is allowed; changing or removing one is a breaking change for every script consuming it.
10. Nothing a subagent does enters the parent transcript except its final message. Its tool calls, tool output, and dead ends are discarded. If that ever breaks, the feature costs two models and still fills the context it was meant to protect.
11. The TUI restores the terminal on every exit path: scroll region reset, raw mode off. A crash that leaves a two-line screen is worse than no TUI.
12. In raw mode Ctrl+C aborts the turn and never kills the process, because the terminal no longer sends SIGINT and the user still expects Ctrl+C to mean stop.
13. Any list drawn above the bars, the palette or the `@` picker, clears the rows it occupied before returning them to the scroll region, including on the way out through Ctrl+D. Otherwise the next line of output drags a stale list up the screen, or axe exits leaving a frozen menu behind.
14. Typing in the palette resets the selection to the first row, so Enter never runs a command the user is no longer looking at.
15. An escape sequence split across two stdin chunks is held back, never decoded as an escape plus typed characters. Only a paste and an unterminated escape sequence are ever held back, and only a paste may be held back at any size.
16. A resize redraws the viewport rather than patching it. The block below the scroll region is axe's, and a resize strands all of it, but its old coordinates cannot be cleared correctly: a grown terminal also pulls rows down out of scrollback by an amount nothing on this side can measure, and a narrowed one re-wraps every row already on screen. The scrollback keeps the transcript either way, which is the part worth protecting.
17. An update is downloaded next to the running binary and renamed over it. Never write the new bytes to the binary's own path: an interrupted write leaves an executable that is half of two versions.

## Verify before claiming done

```
npm test
```

That runs the typecheck, the tool smoke suite, the argument parser, the error classifier, the compaction rules, the loop invariants, the recorded adapter contracts, subagent isolation, skill and custom agent discovery, plugin loading, the diagnostics command, crash recovery, the reliability regression, the TUI editor and palette, the rendered screen, and the update path. All of it must be green before you call a phase done.

`recovery-test` is the suite that writes journals by hand, because the ones worth testing are the ones a crash leaves behind: a turn with no `turn_finished`, a tool journalled as executing and never finished, a torn last line. It also holds the state-file cases — a damaged `schedules.json`, `mcp-approved` or `config.toml` — since each of those carries a comment promising it degrades rather than failing the session, and a promise in a comment is not a test.

`reliability-test` covers what only breaks in time rather than in logic: which statuses are retried and which are not, that a stream is never replayed once it has yielded, that a connect timeout does not cut a slow body, the bash timeout and its process group, background bash, and the schedule wake-up. It fakes `globalThis.fetch` and nothing else, and it asserts delays by computing them rather than by sleeping through them. On a machine with no usable `bash` it says so and skips those cases, because a bash test that does not run bash is not coverage.

`screen-test` is the one suite that runs the renderer: it swaps `process.stdout` for a small terminal emulator and asserts on the resulting grid, which is how the scroll region, the panel, and the ghost rows a list leaves behind are checked. Anything about escape codes that can be stated as "what is on row N" belongs there rather than in a comment.

What `npm test` cannot tell you: whether a provider's wire format still matches the recordings, and whether the TUI actually looks right — colour, glyph width in a real font, and how the panel feels at speed. Only a live call and a real terminal do those.
